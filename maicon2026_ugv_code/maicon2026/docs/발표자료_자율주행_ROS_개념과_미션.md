## 0. 한 장 요약

```
센서(LiDAR·카메라·깊이카메라·바퀴 오도메트리·IMU)
        │            ROS 토픽(/scan /odom TF 영상 …)
        ▼
 ┌────────────── 인지·위치추정 ──────────────┐
 │ SLAM(Cartographer): "나는 지금 어디?" + 지도  │
 │ 검출(YOLO): "저건 무슨 물체?"                  │
 │ 깊이 3D 지도: 낮은 장애물·높이 확인            │
 └─────────────────┬──────────────────────────┘
                   ▼
 ┌──────── 임무 두뇌 (maicon26 Agent, 20 Hz 한 루프) ────────┐
 │ M1 명령 해석 · M2 지정표적 · M3 객체 탐색 · M5 거점 진입 · M6 순위 보고 │
 │ + 적 UGV 회피 + 환경 이벤트(스모그·드론·타워)                          │
 └───────────────┬──────────────────────────────────────────┘
                 │ "여기로 가라"                      │ "팬틸트 각도, 레이저 발사"
                 ▼                                    ▼
          Nav2 (경로 계획·추종)                  서보·레이저(ESP32)
                 │ /cmd_vel_nav2
                 ▼
        Agent의 안전 필터(LiDAR 정지·가감속)  ──/cmd_vel──►  바퀴
```

- **ROS2/Nav2는 "어디로 어떻게 가나"를 맡고, 임무 판단(무엇을 할지)은 Agent가 맡는다.** 둘 사이 경계는 "목표 지점 하나를 주고, 속도 명령을 되받는 것" 하나뿐이라서 서로 독립적으로 시험할 수 있다.
- 안전의 최종 권한은 항상 **Agent의 LiDAR 안전 필터 → STOP 신호** 순이다. Nav2도, 임무 로직도 이 필터를 우회하지 못한다.

## 1. 기본 개념 (비유 포함)

### 1.1 ROS2 — 로봇 소프트웨어의 "우체국"
| 용어 | 뜻 | 비유 | 우리 코드의 예 |
|---|---|---|---|
| **노드(node)** | 하나의 프로그램 | 부서 | `cartographer`, `controller_server`, `maicon26` |
| **토픽(topic)** | 한 방향 방송. 발행자 → 구독자 | 라디오 채널 | `/scan`(LiDAR), `/odom`, `/cmd_vel` |
| **서비스** | 질문 → 대답(짧음) | 전화 | 라이프사이클 활성화 |
| **액션(action)** | 오래 걸리는 일의 요청·진행·결과·취소 | 택배 주문 | Nav2 `NavigateToPose`(목표 전송/취소) |
| **TF** | 좌표계 사이의 변환 트리 | 지도 위 "이 건물은 저 건물에서 북쪽 3 m" | `map → odom → base_link → laser` |
| **시뮬레이션 시계** | `/clock` 로 시간을 외부에서 줌 | 영화 촬영 슬레이트 | `use_sim_time:=true` (시뮬에서만) |
| **QoS** | 전달 보증 수준 | 등기/일반우편 | 센서는 "최신 것만"(best effort) |

핵심 한 줄: **ROS는 "누가 무엇을 방송하고 누가 듣는지"를 이름으로 맞추는 약속**이다. 그래서 실기에서 제일 먼저 틀어지는 것은 알고리즘이 아니라 **토픽·프레임 이름과 단위**다 (§8 일정에 크게 잡은 이유).

### 1.2 좌표계 (가장 많이 틀리는 곳)
```
map        SLAM이 정한 세계 좌표(시작 위치가 원점. 지도 보정으로 조금씩 움직임)
 └ odom     바퀴 거리 적분 좌표(부드럽지만 시간이 갈수록 어긋남)
    └ base_link   로봇 몸체 중심
        ├ laser    LiDAR 위치
        ├ camera / depth_link   카메라(팬틸트 위) / 깊이 카메라(팬틸트 아래, 몸체에 고정)
경기장 좌표  원점=왼쪽 아래 모서리, x 오른쪽, y 위. (우리 코드의 모든 임무 좌표)
```
- **map ↔ 경기장 좌표**: SLAM의 map 원점은 "시작한 자세"라서 경기장과 회전·이동 관계가 있다. `Nav2Stack.start()`가 시작 때 벽을 보고 두 좌표계를 한 번 맞추는 **앵커(anchor)**를 잡는다 (`nav/nav2_stack.py`).
- 각도는 반시계 +, 로봇 전진 = +x, 왼쪽 = +y. LiDAR 장착 방향이 다르면 `LIDAR_ANGLE_OFFSET`으로 보정(제자리 회전 시 지도가 같이 돌면 이 문제).

### 1.3 센서 개념
| 센서 | 무엇을 주나 | 강점 | 약점 | 우리가 쓰는 곳 |
|---|---|---|---|---|
| **2D LiDAR (D500)** | 한 평면(높이 약 0.2 m)에서 360° 거리 | 정확, 빠름(10 Hz), 조명 무관 | 평면 아래·위 물체 못 봄, 투명/연기 취약 | SLAM, 비용지도, **안전 정지**, 객체 박스 군집, 적 UGV 동적 군집 |
| **RGB 카메라**(팬틸트 위, 160° 광각) | 영상 | 물체 종류·색 구분 | 거리 모름(크기로 추정), 어두우면 약함 | YOLO 검출, 수광센서(흰 원판/돔) 찾기, 안테나 색, LED |
| **깊이 카메라(OAK Stereo)** | 픽셀마다 거리(2.5D) | 3D 점, 낮은 장애물 | 가까이(<0.3 m)·멀리 오차↑, 팬틸트 **아래 고정** | 3D 복셀 지도, 사격 전 높이·사선 확인 |
| **바퀴 오도메트리** | 바퀴가 돈 만큼의 이동 | 연속, 부드러움 | 미끄러지면 어긋남(누적 오차) | SLAM의 초기 추정 |
| **IMU(자이로)** | 회전 속도 | 회전 추정 | 편향이 쌓임 | 방향 보정 |

### 1.4 지도 — 2D 점유격자 vs 3D 복셀
- **점유격자(occupancy grid, 2D)**: 바닥을 5 cm 칸으로 나누고 칸마다 "막힘 확률(로그오즈)". LiDAR 광선이 지나간 칸은 비움(-), 끝난 칸은 채움(+). `nav/grid.py`.
  - 우리 코드의 중요한 성질: **모르는 칸(0)을 "비어 있음"으로 취급**한다 → 그래서 "어디를 실제로 훑었나"를 알려면 별도 `SeenMap`이 필요했고, M3 탐색에 새로 만들었다.
- **3D 복셀(voxel)**: 3차원 5 cm 큐브 지도. 깊이 영상 + 카메라 자세(TF) + 로봇 자세를 합쳐서 쌓는다 (`perception/voxel_map.py`, `depth_fusion.py`). LiDAR가 못 보는 12 cm 낮은 장애물, 사선 가림, 표적 높이를 확인.
- 비용지도(costmap): 점유격자 위에 "장애물 근처일수록 비싸다"는 값을 얹은 것. Nav2 경로가 이걸 따라 장애물에서 떨어져 간다.

### 1.5 SLAM, 위치추정
- **SLAM** = 지도를 만들면서 동시에 내 위치를 맞추는 문제. 우리는 **Cartographer(2D)** 또는 **slam_toolbox**를 쓰고, 둘 다 `/scan`+`/odom`에서 `map→odom` TF를 만든다.
- 경기장 박스가 **경기 중에도 바뀔 수 있어서** SLAM의 `/map`(누적 지도)은 Nav2에 쓰지 않는다. 옮겨진 박스가 한동안 유령으로 남기 때문. SLAM에는 **위치(TF)만** 받는다. 장애물은 LiDAR 마킹+지우기(레이캐스트 클리어링)로 매 순간 반영한다.
- 내장 백엔드(시뮬·폴백)는 파티클 필터로 외벽에 정합해 위치를 구한다 (`nav/localize.py`).

### 1.6 Nav2 — "목적지만 주면 알아서 가는" 패키지
```
 Behavior Tree(bt_navigator): 전체 시나리오 (경로 계산 → 따라가기 → 막히면 복구)
   ├ planner_server    전역 경로: 지도 전체에서 최단·안전 경로 (우리: 2 Hz로 자주 다시 계산)
   ├ controller_server 지역 추종: 경로를 따라 속도(v,w) 계산 (RPP: 앞쪽 점을 향해 조향)
   ├ behavior_server   복구: 제자리 회전(spin)·후진(backup)·대기(wait)
   └ costmap 2개       global(전체)·local(주변). 층: obstacle(LiDAR) + inflation(여유 비용)
 입력 액션 /navigate_to_pose   출력 속도 /cmd_vel_nav2 (우리가 일부러 /cmd_vel과 분리)
```
- **footprint**: 로봇 모양. 비용지도가 "이 자세에 몸이 장애물과 겹치나"를 이 모양으로 판정. 우리는 250×230 mm 직사각형 + 여유(§4).
- **inflation**: 장애물 둘레에 "가까울수록 비싼" 띠. 박스 사이 통로가 40 cm라서 반폭 0.115 m + 여유로 지나갈 수 있게 값을 잡는 것이 핵심.
- **A\***: 칸 격자에서 비용이 가장 낮은 길을 찾는 고전 알고리즘. 내장 항법(`nav/navigator.py`)과 폴백이 쓴다. Nav2 전역 계획기와 같은 종류의 문제를 푼다.

### 1.7 "누가 움직이게 하는가" — 명령 소유권
같은 바퀴를 Nav2, 임무 로직, 회피 로직이 모두 움직이려 한다. 그래서 **최종 `/cmd_vel`은 Agent 하나만 낸다.** Nav2는 `/cmd_vel_nav2`로만 말하고, Agent가 받아서 안전 필터를 거쳐 보낸다 (§5).

## 2. 우리 시스템 구조 (코드 지도)

| 층 | 역할 | 주요 파일 |
|---|---|---|
| 하드웨어 추상(HAL) | 로봇 API 한 겹으로 감춤. 임무 코드는 이것만 본다 | `hal/base.py`, `hal/wingbot.py`(실기 스텁), `sim/robot.py`(시뮬) |
| 서버 연결 | START/명령/STOP/이벤트 수신, M1·M3·M6 제출 | `link/*`, `mission/guard.py`, `mission/submit.py` |
| 항법 스택 | SLAM+지도+경로계획을 한 인터페이스로 | `nav/stack.py` → `nav/nav2_stack.py`(Nav2) / `nav/local_stack.py`(내장) |
| 인지 | 검출, 객체 지도, UGV 트랙, 수광센서, LED, 깊이 | `perception/*` |
| 임무 두뇌 | 상태머신 `Agent` (20 Hz) | `mission/manager.py` |
| 안전 | LiDAR 정지, SAFE_STOP, 접촉 감지, 깊이 가드 | `nav/safety.py`, `manager._unsafe_reason/_depth_guard/_stall_check` |
| 보정·실험 | 로봇 파라미터 측정, 현장 실험 | `calib/*`, `field/*` |

**실행 구조**: 임무 로직은 **한 스레드의 20 Hz 루프(`Agent.tick`)**다. 느린 일(서버 통신, YOLO, LLM, rclpy 수신)만 별도 스레드이고, 결과는 잠금/큐를 거쳐 루프가 "가져가는" 방식이다. 이 구조가 경쟁상태(§5)를 크게 줄인다.

## 3. 경기 시간표와 상태 전이

```
0 s     START 수신 → EXPLORE (M1 제출, M2 지정표적 접근·사격, M3 객체 탐색을 병행·교대)
222 s   STAGE  상대 진영 중앙(스테이징 지점)으로 사전 이동 (M3 탐색 마감)
235 s   M3 제출 (t_base_cmd − 5 s)
240 s   목표거점 명령 수신 → GOAL (M5 거점 진입; 표지를 읽어 어느 거점인지 확정)
300 s   STOP → HALT(구동 0·목표 취소) → REPORT(M6 순위 제출, 최대 30 s) → DONE
```
상태: `WAIT / EXPLORE / STRIKE / STAGE / GOAL / RECOVER / SAFE_STOP / HALT / REPORT / DONE`. HUNT(M4: 상대 UGV 사격)는 코드가 있지만 **기본 OFF**.

우선순위(높음→낮음): STOP/HALT → SAFE_STOP(센서 끊김 등) → 발사 잠금 → 적 회피 소유권(EVADE/CLOSE) → M5(GOAL) → RECOVER → 사격 지속 → STAGE → 모드 중재(STRIKE/탐색).

## 4. 미션별 원리 (무엇을 쓰고, 어떻게 동작하나)

### M1 — 자연어 명령 → 구조화 JSON 제출
- **하는 일**: "RADAR를 쏘고 B-S1, B-S2를 정찰한 뒤 …" 같은 한국어 명령에서 *지정표적 종류, 정찰 섹터, 후속 거점*을 뽑아 서버에 제출.
- **개념**: 규칙 기반 파서(정규식·동의어, `mission/command.py`) + 선택적 LLM. LLM이 늦게 와도 현재 명령을 덮지 못하게 **명령 버전(`_cmd_ver`)**을 비교하고, 시간 안에 안 오면 규칙 결과만 제출.
- **쓰는 곳**: 서버 링크, 상태머신. ROS 불필요.
- **현재 상태**: 서버 JSON 키는 예시만 확인(`SCHEMA_VERIFIED=False`), 실제 API는 11/6 멘토링 후 확정.

### M2 — 지정표적 타격 (STRIKE)
1. **찾기**: YOLO가 지정표적 종류(GUARD_POST/RADAR_FACILITY/COMM_FACILITY) 면을 검출 → `ObjectMap`에 위치·법선(바라보는 방향)을 누적.
2. **접근**: 표적 면 앞 약 1.1 m의 **'비어 있고 사선이 트인 점'**을 골라(`_strike_goal`) Nav2/A*로 이동. 면의 법선이 영상으로는 틀리기 쉬워서 **LiDAR 박스 면 장부로 보정**(`_snap_face_normal`).
3. **조준 (비주얼 서보)**: 표적에서 **수광센서(흰 원판 약 6 cm)**를 영상에서 직접 찾아(`perception/receiver.py`) 그 점이 화면의 "레이저가 가는 곳"에 오도록 팬/틸트를 돌린다. 카메라와 레이저가 **같은 팬틸트**라서 카메라가 보는 방향 = 조준 방향이고, 둘 사이 평행 오프셋(시차)만 거리로 보정(`aim.laser_lateral_m` 등, **실측 필요**).
4. **발사**: 정렬이 `hold_before_fire`(0.2 s) 유지 + 사거리 ≤ 접근 목표+0.15 m + 정면각 ≤ 40° + 사선 확인(다른 표적/아군 가림, 깊이 지도로 높이·가림) 통과 시 발사. 2 s 연속 수광이면 유효 타격(규정).
5. **완료**: 서버 이벤트 또는 **표적 시그널 LED 점등을 영상으로 확인**하면 완료 → 탐색 복귀.
- **쓰는 개념**: 검출, 카메라 모델(픽셀→방위각), 팬틸트 서보, 시차 보정, 깊이 3D 확인, Nav2 이동.

### M3 — 전장 객체 탐색·집계 (온라인 탐색)
- **목표**: 박스 면마다 붙은 객체(6종)를 빠짐없이, 중복 없이 세어 섹터별로 제출.
- **예전 방식**: 5×5 격자 점을 순서대로 돌며 점마다 360° 회전(고정 순회).
- **지금(기본)**: ① **SeenMap**(LiDAR로 실제 훑은 곳) ② **면 장부**(박스 면마다 "볼 수 있었는지/가렸는지/분류 확정/빈 면" 상태) ③ **다음 최선 시점(NBV)**: 후보 시점마다 `정보 이득 ÷ (이동시간+관측시간)`을 계산해 가장 좋은 곳으로. 마감(222 s) 전에 못 끝낼 시점은 거절.
- **중복 방지**: 박스 면 1개 = 객체 1개(장부 집계). 박스가 옮겨지면 격자가 "비워짐"을 감지해 옛 면을 지움.
- **정직한 결과**: 정밀도는 올랐고(0.82→0.99) 이동거리는 줄었지만 재현율은 고정 순회보다 약 5%p 낮았다(시뮬). `explore.strategy="lattice"`로 즉시 되돌릴 수 있다.
- **쓰는 개념**: 점유격자, 프런티어, 가시성(시야·거리·입사각·가림), 정보 이득, 비용 경로 추정.

### M4 — 상대 UGV 사격 (기본 OFF)
상대는 움직이고 2 s 연속 수광이 어려워 시뮬 명중률이 낮았다. 대신 **회피(아래)**를 쓴다.

### M5 — 목표거점 진입
- 240 s에 "목표거점은 OO이다" 명령 → 상대 진영의 3개 거점 중 **표지(거점 위 그림)**를 읽어 어느 거점인지 확정(보이면 직접, 둘이 확인되면 소거법). 못 정하면 6 s 후 가장 가까운 후보를 추측.
- 거점 중심으로 Nav2 이동 → 거점 안(여유 −0.12 m)에 들어오면 정지하고 **서버 STOP을 기다림**(광전센서 판정이 공식 종료).
- **시간이 급한 이동**이므로 STAGE/GOAL 중에는 적 회피가 정지·후퇴로 소유권을 가져가지 못하게 했다(경로만 위험을 피함).

### M6 — 상대 UGV 위험도 순위 보고
- STOP 직후 30 s 안에 3대의 순위 제출. 위험도 = 생존(우리 타격 횟수) + 잔탄 + 인식(방문 섹터·이동량)의 가중합 `[가정 가중치]`. **상대 UGV 뒷면 LED(피격 색·8칸 탄창)를 읽으면** 추정 대신 실측값 사용. LLM은 선택(순열 검증 실패 시 규칙 순위).
- 제출은 ACK가 올 때까지 재시도, 30 s 마감.

### 환경 이벤트 (규정 p25 등)
스모그(LiDAR 고립 반사 제거·감속·발사 신뢰도↑), 드론 영상 주기 변화(1→2→5 s→중단 → 트랙 보존 시간 조정), 3색 타워(서버 STOP 유실 시 보조 정지), 표적·UGV LED 판독.

### 적 UGV 회피 (신규)
카메라(YOLO+안테나 색)·UAV·LiDAR 동적 군집 → 위협 보드(적/아군/미상) → 시간 층 위협장(몸이 있을 수 있는 곳 + 맞을 수 있는 곳) → 수준(AWARE→EVADE→CLOSE). EVADE부터 소유권을 가져가 **안전 경유지**로 이동. 정면 추격에서 피격 4.3→1.3(시뮬)이지만 후방·측면에서는 기준선과 비슷, UAV 지연 시 오히려 나빠짐 → **기본 켬 확정 근거 부족**(`avoid.enable`로 끔).

## 5. 경쟁 상태(Race condition) 방지 로직 — 어디서 무엇을 쓰나

> 경쟁 상태 = 두 일이 순서 없이 겹쳐서 "늦게 도착한 옛 정보로 지금 행동을 바꾸는" 오류. 이 프로젝트에서 실제로 위험한 지점을 아래처럼 막았다.

| # | 위험한 상황 | 막는 방법 | 파일/위치 |
|---|---|---|---|
| 1 | 두 모드가 같은 틱에 바퀴·팬틸트를 동시에 명령 | **단일 제어 루프**: 한 틱에 하나의 모드만 실행(디스패치). 출력은 `_apply`/`_stop_output` 한 경로로만 나가고, 한 틱에 두 번 나가면 `multi_output`으로 세어 드러냄 | `manager._decide/_run_mode/_count_output` |
| 2 | STOP이 센서·통신 지연에 막힘 | `tick()` **맨 앞**에서 서버 메시지 처리(`_serve`) 후 STOP이면 즉시 `HALT`(구동 0, 목표 취소, 회피 상태 폐기). 센서가 막혀도 STOP이 먼저 | `manager.tick/_serve/_enter_halt` |
| 3 | 같은 START 중복, 지난 경기의 늦은 메시지 | **MatchLatch**: START는 1회, STOP은 종단(되돌릴 수 없음), `match_id`·순번 `seq` 검증, 정지 중 다음 경기 메시지는 보관했다가 새 Agent에 전달 | `mission/guard.py` |
| 4 | 느린 제출/영상 수신이 STOP 수신을 늦춤 | 서버 연결을 **3 스레드**(poll / UAV / submit)로 분리, 한쪽이 예외·지연이어도 다른 쪽 영향 없음 | `link/async_link.py` |
| 5 | 취소·교체된 목표의 늦은 결과·속도가 새 목표에 섞임 | **epoch(세대) 번호**를 올리고 `clear_goal()`로 목표 취소. Nav2 쪽은 **CmdCache 문**: 목표 전송/취소 때 캐시를 비우고 문을 닫아 이후 속도를 버리고, 서버가 새 목표를 **수락**한 뒤에야 문을 열어 그 뒤 속도만 채택(Nav2 속도 메시지에는 목표 ID가 없음) | `manager._set_mode/epoch`, `nav/cmd_cache.py`, `nav/ros_nav2.py` |
| 6 | Nav2 속도와 임무/회피 속도가 충돌 | Nav2는 `/cmd_vel_nav2`로만 출력, **Agent가 안전 필터를 거쳐 `/cmd_vel` 단독 발행**(명령 중재) | `ros2/README.md`, `Nav2Stack` |
| 7 | 센서 시계가 로봇 시계와 달라 자세가 어긋남 | **StampSync**(같은 시계면 그대로, 다르면 오프셋·최소 지연 보정) + **자세 이력(`pose_at`)**: 센서는 "도착 시각"이 아니라 **촬영 시각의 자세**와 짝지음 | `hal/clock.py`, `manager.pose_at` |
| 8 | 비동기 YOLO가 이전 프레임 결과를 줌 | 프레임을 `deque`에 보관하고 **그 결과가 나온 프레임의 stamp·자세·팬틸트**와 묶어 한 번만 반영(`_det_consumed`) | `manager._ingest_vision` |
| 9 | 늦게 온 옛 UAV 프레임이 새것을 덮음 | UAV는 **단조 증가하는 촬영 시각만** 수용 | `manager._sense` |
| 10 | LiDAR가 끊겼는데 계속 주행 / 복귀 후 옛 상태 재개 | **SensorWatch**(도착 시각 기준 신선도 0.6 s) → SAFE_STOP. 복귀는 새 표본 N개가 들어와야, 그리고 이전 상태를 맹목적으로 재개하지 않고 EXPLORE부터 | `guard.SensorWatch`, `manager._unsafe_reason/_decide` |
| 11 | 피격 이벤트가 하드웨어 상태보다 먼저/늦게 옴 | **Locks**: 발사/틸트 잠금과 주행 잠금 분리, 하드웨어 상태가 최종 권한, 이벤트만 먼저 오면 짧은 유예(grace)만 보수적으로 잠금(4번째 피격부터 주행도) | `guard.Locks` |
| 12 | 제출 중복·누락 | **Submitter**: ACK까지 재시도·백오프, STOP 뒤 M1~M5 신규 제출 금지(M6만), 포기한 M1/M3 재시도 | `mission/submit.py` |
| 13 | 늦은 LLM 응답이 새 명령을 덮음 | 명령 버전 비교 후 오래된 응답 폐기 | `manager._poll_llm` |
| 14 | 모드가 번갈아 뒤집힘(채터링) | 모드 최소 유지 1.2 s, **발사 중에는 모드 전환 금지**, 회피 수준 진입/해제 문턱 분리 + 해제는 한 단계씩, EVADE 재진입 횟수 제한 | `manager._decide`, `mission/avoid.py` |
| 15 | 회피↔임무 소유권 전환 중 옛 목표가 남음 | 전환 때 `clear_goal()`+`epoch++`+사격 중단+관측 상태 초기화, 복귀 땐 **옛 목표를 이어가지 않고 새로 정함**, M2는 3 s 쿨다운 후 조준부터 다시 | `manager._on_avoid_acquire/_on_avoid_release` |
| 16 | Nav2가 목표 근처 재전송 폭주 | 목표가 0.15 m 넘게 바뀔 때만 재전송, 경유지(carrot)는 0.45 m 안으로 접근할 때까지 고정 | `nav/nav2_stack.py`, `manager._risk_carrot` |
| 17 | 움직이는 다른 UGV 때문에 경로 재계획이 요동 | 경로 무효화는 **로그오즈 ≥1.8(정적 구조물)**인 새 칸만 반응(UGV 표면은 1~2회만 맞아 무시) | `nav/navigator.py` |
| 18 | rclpy 콜백 스레드와 제어 루프의 데이터 경합 | 지도·속도·상태는 `threading.Lock`으로 보호, rclpy spin은 별도 스레드 1개(`ros_runtime`), 종료 순서 정리 | `nav/ros_nav2.py`, `nav/ros_runtime.py` |
| 19 | Nav2 서버가 죽었는데 목표만 재전송 | 서버 부재 1.5 s 또는 한 목표 연속 실패 시 **내장 A\*로 폴백**(그 목표만) | `Nav2Stack._enter_fallback` |

**한 줄 원칙**: (1) 쓰기는 한 곳, (2) 취소할 때는 세대 번호로 늦은 결과를 거르고, (3) 센서는 촬영 시각으로 맞추고, (4) STOP은 항상 맨 앞, (5) 모르면 멈춘다.

## 6. 산출물과 "측정해야 하는 값"

### 6.1 산출물 (코드가 만드는 파일)
| 산출물 | 내용 | 만드는 법 |
|---|---|---|
| 로봇 모델 | URDF, 시뮬 구동 설정 | `calib_generate.py` |
| 구동 보정표 | 최대 속도·가속도·회전·**속도별 정지거리**·좌우 편차·주행면별 슬립 | `calib_run.py` → `calib_fit.py` |
| 센서 보정 | LiDAR/카메라/IMU 장착 TF, 카메라 내부 파라미터, 지연 | 위 + 체커보드 |
| 항법 설정 | Nav2 footprint·여유거리·추종 속도·복구, `robot_calibrated.json` | `calib_generate.py` |
| 현장 기록 | 측정 CSV, rosbag, `config/field_overrides.json` | `calib_run.py`, `field_exp.py` |

단일 출처: `calib/robot_profile.yaml` (값마다 `pdf / assumed / measured` 표시). **PDF에 없는 것은 전부 `assumed`**이고, 측정하면 `measured`로 바뀌며 Config와 Nav2 설정이 함께 다시 생성된다.

### 6.2 측정해야 하는 값 (ROS·항법 관련 우선)
| 분류 | 값 | 어떻게 재나 | 틀리면 |
|---|---|---|---|
| **이름·단위** | 토픽명(`/scan /odom /cmd_vel`), 프레임명, 깊이 인코딩(mm?), 시계 | `ros2 topic list/echo`, F01 | 아무것도 안 움직임 |
| **차체** | 길이·폭(바퀴·안테나 포함), 바퀴 반경·간격, 질량 | 줄자 (F09) | 통로 통과·충돌 판정 |

| **LiDAR 오차** | 거리 편향·잡음, 각도 오차, 장착 오차, 전달 지연, 누락·이상치 비율 | 정지 벽 0.3/1/2 m 반복, 스캔 stamp | 여유거리·정지거리 |

| **오도메트리/IMU** | 선형·회전 스케일, 자이로 편향 | `static/straight/rotate` | 위치 드리프트 |
| **RGB 카메라** | 내부 파라미터 K·왜곡, 화각, 지연 | 체커보드(`calib_fit --camera-images`) | 방위각·거리 추정 |
| **깊이 카메라** | 설치 위치(`rig.depth_xyz`)·각도, K, 최소/최대 유효거리, 오차 | 줄자 + F02(바닥면) F03(벽) F04(LiDAR 정합) | 3D 지도가 어긋나 쌓임 |

| **수광** | 수광센서 유효 거리·각도, 표적 창 크기 | 실물 | 사거리·사선 판정 |
| **경기장** | W/H, 거점 중심·크기, 박스 간격, 벽 높이 | 줄자 (F09) | 앵커·거점 판정 |
| **통로** | 40 cm 통로 직진·비스듬한 진입·**제자리 회전 가능 반경** | 실주행 | footprint/inflation |

## 7. "학습해야 하는 값" (데이터로 만드는 것)

측정은 줄자·계측으로 값을 재는 일이고, **학습**은 사진·영상 데이터로 모델/임계값을 만드는 일이다.

| 대상 | 무엇을 | 데이터 | 비고 |
|---|---|---|---|
| **YOLO 검출기** | 객체 6종(AMMO_BOX, DRUM, MORTAR, TRUCK, TANK, MISSILE), 지정표적 3종, UGV, (비인식용 4종), 거점 표지 3종 | 사전 제공 이미지 + 대회장 촬영 | **가중치 파일이 아직 없다**(코드에 래퍼만 있음). RTX 5070 PC에서 학습 → `.pt/.engine/.onnx` 배포. 클래스명 ↔ `vocab.py` 키 매핑(`names_map`) |
| **UGV 안테나 색(팀 판정)** | 적/아군 구분 HSV 임계 또는 분류기 | 현장 사진(거리·각도별) | 오판 비율이 회피 성능을 좌우(`r_cam` 가정 0.80) |
| **수광센서 검출** | 흰 원판/흰 돔 HSV·크기 임계 | 실제 표적·UGV 사진 | `perception/receiver.py` |
| **LED 판독** | 표적 시그널 LED, UGV 뒷면 LED, 3색 타워 | 실물 영상 | `perception/led.py` |
| **UAV 영상 → 위치** | 드론 영상에서 UGV 검출·좌표 변환 | 드론 영상 | **코드에 없음**(서버 `get_uav()`도 스텁) |

ROS 파트에서의 "학습"은 사실상 **없다**(SLAM·Nav2는 학습 모델이 아니라 파라미터 튜닝). 학습은 인지(YOLO·색·LED) 쪽이다.

## 9. 발표 시 강조할 한계 (정직한 상태)
1. 실기 측정값 0개 — 모든 수치가 시뮬 결과이거나 가정(`field/FIELD_CHECKLIST.md` 참조).
2. YOLO 가중치, UAV 영상 검출기, 서버 API가 없어서 그 입력은 시뮬이 주는 값으로 대체해 검증했다.
3. M3 온라인 탐색은 재현율이 고정 순회보다 낮았다(정밀도·이동거리는 개선). 선택 가능하게 둠.
4. 적 회피는 정면 추격 외에서는 이득이 불분명하고, 센서 품질이 나쁘면 오히려 나빠질 수 있어 기본값 확정 전 현장 검증 필요.
5. 실제 Nav2는 한 번의 실행으로 판단하지 말 것 — 반복 시험(≥10회)이 기준.
