# 경기 서버 통신의 견고성

2026-11-04 안내서 스냅숏에 맞춘 2026-11-09 구현 기록이다. 실서버에는 접속하지 않았다.
전체 회귀는 사용자 요청으로 중단됐으며 새 경기장 재구성 이후 다시 검증해야 한다.
개별 시험 성공을 전체 또는 ZIP 내부 검증 완료로 확대하지 않는다.

## 제어 루프와 통신 분리

실전 `run_real.py`는 항상 `AsyncServerLink`를 사용한다. 제어 루프를 동기 요청에 노출하던 `--sync-link`는 제거했다.
HTTP의 /me·/order·/target는 별도 작업 스레드이고 영상과 제출도 비동기로 처리한다.
Agent의 poll은 준비된 메시지만 읽는다. 시작·정지는 로봇 match와 서버 phase 중 먼저 받은 신호를 반영한다.
pause는 정지 명령이지만 경기 종료와 M6 제출 신호가 아니다.

## 요청과 재시도

| 경로/상황 | 정책 | 근거·제한 |
| --- | --- | --- |
| 일반 요청 | 기본 timeout 3초 | 모든 urllib 요청에 제한 전달 |
| /order, /target | 기본 wait 20초, 범위1~120초; HTTP timeout=wait+max(5초,일반 timeout) | 위험 #1: timeout이 wait보다 짧아 정상 긴 폴링을 실패로 보던 문제 방지. 20초는 허용범위 내 운영 선택 |
| 준비 | 초기화·편성 확인 후 ready; 실패 시2초 뒤 me부터 | 모델/센서 실패 시 ready 금지 |
| 게시 전 accepted:false | 0.5초 후 재요청 | HTTP200 정상 대기, 오류로 집계하지 않음 |
| 미편성 | 10초 대기하며 me 확인·운영자 안내 | 기다리면 게시될 것으로 가정하지 않음 |
| 게시 누락·리허설 비활성 | 5초 후 재확인 | 경고는 내용 변경 때만; 누락 게시를 합성하지 않음 |
| 알 수 없는 reason | 값 마스킹·길이 제한 후1초 재확인 | 미안내 동작을 분류하지 않음 |
| 401/422 | 오류를 가린 뒤 느리게 재시도/제출 거절 처리 | 현장 코드 교체는 set_mission_code; 이전·신규 코드 모두 마스킹 유지 |
| 통신 실패·5xx | 0.5초부터 지수 증가, 최대5초 | 취소 가능한 Event 대기 |
| 제출409 | 미편성·제외·미출발은 해당 임무 영구 중단, 단계 불일치는 제한 재시도 | G3. 다음 경기는 링크를 새로 생성 |
| accepted:true의 received 불일치 | ACK로 인정하지 않고 같은 본문 최대1회 추가 전송 | G1. M1/M3 순서·대소문자 차이는 정규화, M6 순위 순서는 의미 유지 |
| ACK 지연 | 같은 token 큐 중복 방지, 결과는 token별 수집 | 응답 유실 때 서버가 이미 저장했을 가능성을 인정, 전체 대체 본문으로 재전송 |

## 제출 마감

M1은 규칙 해석으로 먼저 보고하고 제한 시간 안의 유효한 LLM 결과가 있으면 전체를 정정한다.
M3는 확정 관측의 전체 스냅숏을 변경될 때 보낸다. 기본5초 간격이며225초부터1초 간격이다.
표본이 교정되면 개수가 줄어드는 전체본도 보내므로 잘못된 누적 보고를 유지하지 않는다.

STOP/reporting을 받은 틱에서 Submitter의 M1/M3를 먼저 닫는다. 비동기 큐와 HTTP 전송 직전에도 허용 상태를 확인한다.
전환 전에 이미 나간 요청을 회수할 수는 없으며 서버 수신 시각으로 거절·수락된다.
M6는 경기 중 관찰 추정으로 만든 순위를 즉시 제출한다. 아직 끝나지 않은 LLM을 기다리지 않는다.
이미 reporting인 재시작도 최초 Agent 틱 전에 STOP을 선반영한다. finished에서는 새 보고를 만들지 않는다.

Agent 단위 STOP 테스트와 실제 HTTP/큐 경계 테스트를 보존한다.
Agent→HttpServerLink→MockServer 전체 연결에서 M1/M3 신규 POST=0 및 M6 수신1초 이내를 한 번에 확인하는
`tests/test_spec_conformance.py` 시나리오 6개는 선택 검증을 통과했다. 전체 회귀·실기 네트워크 인수는 별도이다.

## 시간·재시작

ClockSync는 HTTP Date와 송수신 단조시각으로 오프셋·불확실도를 기록한다.
명령의 한국 시간 issued_at으로 경기 경과를 복구하며 음수·300초 초과·동기 미완료는 버린다.
target의 게시시각은 약240초 차이인지 진단에만 사용하고 목표나 시계를 바꾸지 않는다.
정수 초 Date/issued_at와 네트워크 비대칭 때문에 실기 시각 정확도는 별도 측정해야 한다.

시간을 복구했다고 위치가 복구되는 것은 아니다.
실전 CLI는 실행 중인 경기에서 지도·SLAM 앵커가 복원되지 않은 재시작을 정지 상태로 차단한다.
초기화 이후 me는 확인하지만 준비완료나 주행을 시작하지 않는다.
reporting 재시작은 정지한 채 M6만 진행할 수 있다. G14는 이 한계를 포함한 API 시간 복구이다.

## 영상·비밀값·남은 위험

| 위험 | 현재 대책 | 남은 검증 |
| --- | --- | --- |
| 오래되거나 깨진 UAV 화면 | Captured-At 중복·역행 제거, 간격 양수·유한수 검사, 메타데이터 보존 | 실카메라 지연·렌즈 보정 |
| 영상 camp와 편성 불일치 | me slot/camp 우선, 영상만으로 slot 생성 금지 | 실제 서버 헤더 |
| 임무코드·토큰 출력 | 환경/파일/비표시 입력, 즉시 secret 등록, 대소문자·예외·서버 echo 마스킹 | 현장 비표준 비밀 파일은 배포 제외 추가 |
| 오류 본문 형식 차이 | list/dict/string/nonJSON을 마스킹 후 길이 제한 | 공식422는 loc/msg 목록; 다른 형태는 방어 정책 |
| 서버가 idle로 되돌아감 | 기존 경기 상태를 새 경기로 재사용하지 않음 | 다음 경기 프로세스/링크 재생성 필요 |
| 정지 신호보다 늦게 도착한 POST | 큐 취소+전송 직전 phase 확인, 수신시각 심판 | 이미 전송 중인 요청은 서버 판정 |
| 실제 네트워크 장애 | in-process MockServer와 기존 loopback 결함 회귀 | 실경기 서버·무선 환경은 미검증 |
| 전체 회귀와 배포 | 기존 테스트 보존, 선택 회귀·정적 검사 수행 | 중단된 전체/ZIP 내부 재검증 미완료 |

FakeClock 기반 MockServer는 단일 결정적 시간선이다.
무한 실시간 백그라운드 작업을 동시에 돌리면 가짜 시간이 급진행할 수 있어 테스트는 제한된 스텝과 명시적 종료 조건을 쓴다.
실제 동시성은 기존 loopback·비동기 큐 테스트로 분리한다.
