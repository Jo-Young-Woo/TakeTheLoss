# Waveshare 기반 MAICON 실기 통합

2026-11-07 후속 개선은 [위키 반영 내역](Waveshare_위키_반영_2026-11-07.md)을 함께 읽는다. `TEAM_LAUNCH_NAV=1`은 현재 Agent와 같은 설정에서 프레임·센서·주행 토픽을 전달하며, Ollama 어댑터와 실기 깊이 보정 검증이 추가되었다.

검토·구현일: 2026-11-06. 기존 임무 알고리즘을 보존하고 하드웨어/서버 경계와 실행 수명을 다시 구현했다. 제조사 운영 프로그램을 교체하거나 직접 시리얼 포트를 열지 않는다.

## 기준 자료와 우선순위

- `prestudy(1)_2026MAICON.pdf`: M1~M6 의미, 5분 경기/4분 거점 명령/종료 후 30초 보고, 객체·표적·경기장 규격.
- `prestudy(2)_2026MAICON.pdf`: `/mil/*`, `/cmd_vel`, `/odom`, 카메라·IMU, 팀 노드 실행 규칙. 제조사 일반 API보다 대회 전용 API를 우선한다.
- [서버 API p0~p12](https://maicon.kr/wp-content/kossa/2026MAICON/game-server-api.html#p0): HTTP 요청·응답 및 제출 JSON. PDF의 설명용 JSON과 다르면 구체적인 서버 명세로 변환한다. 원문의 보고 JSON은 임시 형식으로 표시되어 있어 현장 변경 여부를 확인해야 한다.
- [Waveshare ros2-humble-develop](https://github.com/waveshareteam/ugv_ws/tree/ros2-humble-develop), 확인 커밋 `f0b3ad9c16e7acb6d6145f261116d71bf6338f4a`: 제조사 드라이버·EKF·프레임 구성. 이 브랜치의 launch가 대회 로봇에서 그대로 실행된다고 단정하지 않는다.

API 각 페이지는 [서버 대응표](server_api_compliance.md), ROS 구성은 [ROS 연결 문서](waveshare_ros_integration.md), 센서·서비스는 [HAL 연결 문서](hardware_integration.md)에 기록했다.

실행한 테스트와 남은 한계는 [통합 검증 기록](실기_통합_검증_2026-11-06.md)에 정리했다.

## 실행 구조

```text
운영진 Waveshare/MIL 베이스 (기존 실행)
  ├─ /scan, /odom, /imu/data, /image_raw, /mil/state, /mil/match
  ├─ odom → base_footprint → base_link 및 센서 TF
  └─ /mil/gimbal, /mil/fire
팀 SLAM/Nav2 overlay
  ├─ map → odom
  └─ /cmd_vel_nav2 (로봇에 직접 보내지 않음)
team_node → run_real → Agent
  ├─ 센서/모델/TF/서비스 사전 확인 → 서버 /ready
  ├─ M1~M6 / 온라인 탐색 / 면 장부 / 회피
  ├─ 최종 명령 중재 → /cmd_vel 단독 발행
  └─ HTTP 수신·보고 / 종료 후 stop 대기 / 자식 프로세스 정리
```

기본 실기 설정은 `config/waveshare_real.json`이다. 일반 시뮬레이션의 `config/default.json`을 덮어쓰지 않는다. 실기 프레임은 `base_footprint`, 시뮬 기본값은 `base_link`로 구분한다. `/odom`은 제조사 EKF 출력으로 받으며 팀이 IMU를 다시 적분해 별도 odom TF를 만들지 않는다.

## 실행 순서 (로봇의 ROS2 Humble 환경)

프로젝트 디렉터리에서 실행한다. 운영진 베이스 노드와 필요한 ROS 패키지가 먼저 준비되어 있어야 한다. 아래 명령을 Windows PowerShell에서 직접 실행하는 것은 아니다.

```bash
cd <저장소>/maicon2026_ugv_code/maicon2026
source /opt/ros/humble/setup.bash
# 운영진이 안내한 Waveshare/MIL 워크스페이스의 install/setup.bash도 source
ros2 launch ros2/launch/maicon_waveshare.launch.py
```

별도 터미널:

```bash
cd <저장소>/maicon2026_ugv_code/maicon2026
source /opt/ros/humble/setup.bash
# 이 터미널에서도 운영진 워크스페이스의 install/setup.bash를 source
python3 scripts/run_real.py --preflight-only
```

이 명령은 센서·TF·서비스 가용성을 확인하고 종료한다. 구동/레이저/팬틸트 명령으로 성능을 시험하지 않는다(종료 및 주행 안전 유지용 0 속도는 발행). 서버 요청도 하지 않는다. 60초 안에 준비되지 않으면 원인을 출력하고 실패하며, 시간이 지났다는 이유로 준비완료를 보내지 않는다.

실제 임무:

```bash
export MAICON_MISSION_CODE='<현장 임무코드>'
python3 scripts/run_real.py --server http://<서버IP>:8000 --detector /path/to/team_model.pt
```

YOLO는 로컬 파일을 명시해야 한다. 필수 클래스는 객체 6종, 지정표적 3종, UGV, 거점 표지 3종이다. 이름이 다르면 `--names-map mapping.json`으로 내부 클래스에 매핑한다. 모델 로드뿐 아니라 실제 첫 카메라 프레임 추론이 성공해야 `/ready`를 보낸다. 기본 SimDetector로 실기 임무를 실행하지 않는다. 학습된 가중치는 이 저장소에 포함되지 않는다.

공식 자동 실행은 실제 설치 위치의 `team/team_node.py`를 `~/team/team_node.py`로 심볼릭 링크해 코드 루트가 유지되게 한다. 파일 하나만 복사하면 상대 경로를 찾지 못한다.

```bash
mkdir -p ~/team
ln -s /absolute/project/team/team_node.py ~/team/team_node.py
export MAICON_SERVER='http://<서버IP>:8000'
export MAICON_MISSION_CODE='<현장 임무코드>'
export MAICON_DETECTOR='/path/to/team_model.pt'
export TEAM_LAUNCH_NAV=1
# 운영진 프로그램이 ~/team/team_node.py를 실행
```

이미 같은 SLAM/Nav2가 실행 중이면 `TEAM_LAUNCH_NAV`를 켜지 않는다. 기존 SLAM만 이용할 때는 별도 launch의 `slam:=none`을 사용한다. 다른 Nav2나 텔레옵이 `/cmd_vel`을 발행하는 상태에서 함께 실행하지 않는다. 다른 터미널에서 export한 변수는 운영진 프로세스에 자동 전달되지 않으므로 운영진 실행 환경에 변수와 모델 경로를 설정해야 한다.

## 임무별 명세 반영

| 임무/규칙 | 코드 처리 |
|---|---|
| M1: 명령 해석, 탐색 구역·후속 거점은 보고용 | 기존 파서+선택적 LLM 및 schema 변환. M1 거점으로 실제 M5 목적지를 정하지 않음 |
| M2: 지정표적, 2초 연속 수광 | 지정표적 접근·수광부 조준 유지. 유효타격은 장치 판정이며 성공 HTTP를 임의 생성하지 않음 |
| M3: 박스 옆면별 객체, 상대 진영+공통 구역 보고 | 온라인 탐색·면 장부 유지. 전체 집계 스냅숏을 공식 코드로 변환·제출 |
| M4: 상대 UGV | 기존 팀 전략대로 교전 기본 OFF, 위험 회피는 유지. LiDAR 군집은 적군 확정 정보가 아님 |
| M5: 4:00 이후 별도 목표 명령 | `/target` 수신 후 해당 거점으로 전환. 임의 목표를 만들어 서버에 보고하지 않음 |
| M6: 종료 후 최대 30초 | 종료 시 관측 증거 스냅숏으로 순위 생성, LLM 연결 시 비동기 보완, `/situation` 제출 |
| 대회 동작 잠금 | mode/cmd를 수신하기 전 및 mission의 start/resume 외 상태에서 구동·조준·발사 차단 |
| 발사·팬틸트 | 팬 오른쪽+를 내부 왼쪽+로 변환, API 위치 단위와 각도 분리. 응답 유실을 성공으로 처리하지 않음 |
| 종료 | 한 프로세스 한 경기. 보고 완료 후 `/mil/match stop`까지 정지 대기하고 종료 |

## LLM 연결

공식 서버 API에 범용 LLM 추론 엔드포인트는 없다. 임의 엔드포인트를 만들지 않고 `--llm-factory team_llm:create_client`(또는 `MAICON_LLM_FACTORY`)로 팀 어댑터를 연결한다. factory는 인자 없이 호출되며 `complete(prompt: str, timeout: float) -> str`를 구현한 객체를 반환한다. API 키는 어댑터의 환경변수에서 읽고 출력하지 않는다. 시간제한을 지키고 문자열을 반환해야 한다.

LLM이 연결되면 M1 명령마다 호출하고 M6에도 사용한다. 미연결/실패/시간 초과에는 규칙 기반 결과로 대체하며, 이를 LLM 임무 수행 검증 완료라고 표현하지 않는다. 운영 모델·인증·네트워크 연결은 팀이 제공해야 한다.

## 아직 실측 또는 추가 구현이 필요한 항목

- **경기 도중 프로세스 재시작:** 시계만 복원하면 SLAM 원점/앵커와 현재 위치가 맞지 않을 수 있다. 실기 진입점은 start/resume/pause 상태에서 새 임무를 시작하지 않는다. 자동 재개에는 현재 지도·앵커·미션 장부의 일관된 복원이 추가로 필요하다. `--restore`만으로 해결되지 않는다.
- **깊이/복셀:** 실제 OAK 토픽·K·외부 파라미터를 검증하기 전에는 실기 프로필에서 비활성화한다. 시뮬레이션 복셀 기능은 유지한다. 활성화 시 Agent와 launch의 `depth_obstacles` 설정을 함께 맞춰야 한다.
- **UAV:** 공식 JPEG와 캡처 헤더는 보존하지만, 지상 좌표를 생성하지 않는다. 영상 보정·UGV 검출·호출부호 연결은 별도 구현이 필요하다. 이를 실시간 전장 정답 좌표로 취급하지 않는다.
- **크기·마찰·구동:** PDF의 250×230×320mm를 반영한 기존 외곽을 유지하되 진행축 방향은 현장에서 확인한다. 제조사 0.175m 구동 간격, 카메라 시야각, 센서 장착값, 정지거리·슬립은 대회 기체 실측값으로 확정하지 않는다.
- **시계:** 실기 기본은 pause 중에도 로컬 경과시간을 유지한다. 공식 문서에 없는 일시정지 시간 보정은 추정하지 않는다. 운영진이 경기시계 정지를 확정하면 `hal.freeze_clock_on_pause`를 변경한다.
- **현장 판정:** 실물 구동·레이저·최종 거점 센서·실제 HTTP 인증은 미검증. 모의 테스트 통과를 대회 성공률로 해석하지 않는다.

## 검증 명령

```bash
python3 -m pytest -q -p no:cacheprovider tests/test_server_link.py tests/test_hardware_contract.py tests/test_mil_hal.py tests/test_odom_tf.py tests/test_real_preflight.py tests/test_real_runtime.py tests/test_llm_integration.py tests/test_ros_hardware_launch.py tests/test_state_machine.py tests/test_nav_stack.py tests/test_units.py
```

Windows에서 테스트할 때는 자식 Python까지 UTF-8을 쓰도록 먼저 `$env:PYTHONUTF8='1'`을 설정한다. `python -X utf8`만으로는 별도 프로세스의 출력 인코딩까지 바뀌지 않는다.

WSL ROS2 Humble에서 launch 인자, 중첩 costmap 프레임 변경, 실제 노드 기동과 속도 토픽 분리를 확인했다. 무센서 상태라 Nav2 활성화·주행 성공은 시험하지 않았고, 이 상태의 종료 시 controller_server lifecycle 오류(-6)가 관측되었다. 실제 센서를 연결한 활성화/종료 재검증이 필요하다.
