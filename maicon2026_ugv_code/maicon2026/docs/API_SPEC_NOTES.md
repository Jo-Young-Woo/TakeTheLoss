## 0. 공통 연결·시간·보안 — S0

서버 주소는 현장에서 안내하는 `http://<서버IP>:8000`이다. 경기 API 접두사는 `/api/report`, 리허설은 `/api/rehearsal`이다. 실제 접속 주소·임무코드·토큰은 이 문서나 패키지에 넣지 않는다. 안내서의 팀 이름·토큰·시각도 설명용 값이다.

| 메서드 | 경기 경로 | 역할 |
| --- | --- | --- |
| GET | `/api/report/me` | 배정·단계·준비완료 상태 |
| POST | `/api/report/ready` | 준비완료 |
| GET | `/api/report/order` | 1차 전술명령 |
| GET | `/api/report/drone` | 선택적 상공 JPEG 영상 |
| POST | `/api/report/interpretation` | M1 해석 보고 |
| POST | `/api/report/detection` | M3 객체 보고 |
| GET | `/api/report/target` | 2차 M5 목표거점 |
| POST | `/api/report/situation` | M6 위험도 순위 |

임무코드는 영문·숫자 8자리이고 대소문자를 구분하지 않는다. GET은 `mission_code` 쿼리, POST는 JSON 본문의 `mission_code`에 싣는다. POST의 Content-Type은 `application/json`이다. 코드·토큰은 로그, 오류·예외 본문, 추적 정보에 노출하지 않는다. 대소문자가 달라진 서버 오류나 URL 쿼리도 가린다.

서버는 참가팀에게 먼저 푸시하지 않는다. 팀이 상태와 임무를 요청한다. **보고의 마감은 요청을 만든 시각이 아니라 서버가 받은 시각**이다. 단계가 바뀐 뒤 도착한 보고는 409이다.

| 시작 신호 후 | 경기 흐름 |
| --- | --- |
| 0:00 | UGV 잠금 해제·출발, 1차 전술명령 게시 |
| 4:00 | 종료 60초 전, 진영별 M5 목표거점 게시 |
| 5:00 | 진행 종료, M6 보고 30초 시작 |
| 5:30 | 보고 종료, 주최측이 팀 프로그램 종료 |

시작 신호를 받은 순간이 팀 시계 0:00이다. 서버는 남은 시간을 제공하지 않으므로 팀은 자기 시계로 경과 시간을 센다. M5 점령으로 5분 전에 끝날 수 있다. 종료는 로봇의 `report` 신호 또는 `/me`의 `reporting` 단계로 인지하며, 팀 시계가 5분이 되기만을 기다리지 않는다.

흐름도의 역할은 참가팀 `team_node.py`(젯슨), 주최측 경기 노드·ESP, 경기장 카메라·표적·거점, 경기운영 서버이다. 시작·일시정지·보고와 주행·발사는 이 HTTP API가 아닌 젯슨 API 규격을 따른다. 보고 단계에는 UGV가 잠겨도 팀 프로그램은 M6를 위해 계속 실행된다. `finished` 이후 프로그램이 종료되면 추가 보고를 전송할 수 없다.

서버는 남은 시간, 자기 점수, 참가팀 구현 예제 코드를 제공하지 않는다. JSON 형식·주소를 바탕으로 팀이 구현하고, M6는 관측으로 추정한다.

## 1. 준비완료 — S1

주최측 경기 노드가 준비 단계에서 팀 프로그램을 실행한다. 모델과 필수 센서 초기화가 성공한 뒤 `/me`를 조회한다. `phase == "ready"`이고 `ready == false`일 때 임무코드만 담아 `/ready`로 보낸다. 성공은 HTTP 200과 `{"accepted": true}`이다. 409 또는 통신 실패이면 **2초 뒤 `/me`부터 재시도**한다. 사람이 누르는 준비 단추를 대신하는 자동 절차이다.

준비완료를 보내지 않은 팀은 경기에서 제외될 수 있고 빠진 경기는 0점이다. 서버가 모델의 실제 초기화 완료 여부를 검사해 주지는 않으므로 팀이 이를 보장해야 한다.

| `/me` 필드 | 의미 |
| --- | --- |
| `slot` | `B-1`~`B-3`, `R-1`~`R-3`; 이번 경기 배정이 없으면 `null` |
| `camp` | `BLUE`, `RED`; 배정이 없으면 `null` |
| `phase` | 아래 단계 값 |
| `ready` | 서버가 준비완료를 받아 둔 상태, boolean |

| phase | 의미 | 접수 |
| --- | --- | --- |
| `idle` | 경기 열리기 전, 팀 프로그램 실행 전 | 준비완료 대상 아님 |
| `waiting` | 운영진 점검·UGV 배치 | `/ready`는 409 |
| `ready` | 경기 설정을 받은 UGV 잠금, 팀 프로그램 실행 | `/ready` |
| `running` | 0:00부터 진행 중 | 임무 조회, M1·M3 |
| `reporting` | 경기 종료 후 UGV 잠금, 보고 30초 | M6 |
| `finished` | 보고 종료, 팀 프로그램 종료 | 추가 보고 불가 |

이미 준비완료를 접수했다면 재시작 후 `/me`에 `ready:true`가 남는다. 배정이 `null`이면 예전 슬롯이나 임의 BLUE/2를 대신 사용하지 않는다.

오류는 401(잘못된 임무코드), 422(본문·필수 필드 오류), 409(준비 단계 아님·경기 시작 직전·미편성·UGV 설정 미확인)이다. 설정 미확인 문구는 다음과 같다.

> UGV 경기 설정이 아직 확인되지 않았습니다 — 잠시 뒤 다시 보내세요

다른 `/ready` 409의 완전한 문장은 원문에 모두 제시되어 있지 않다. 모의 서버의 사유 표현을 실제 서버의 확정된 전체 문구로 취급하지 않는다.

## 2. 전술명령과 긴 폴링 — S2

`GET /api/report/order`는 0:00에 게시되는 우리 팀의 전술명령을 받는다. 준비완료 직후부터 `wait=120`으로 걸어 두는 것이 안내서의 사용 예이다. 팀마다 명령이 다를 수 있고 다른 팀의 명령을 조회할 수 없다.

| wait | 공식 의미 |
| --- | --- |
| 생략 또는 0 | 즉시 응답 |
| 1~120 | 최대 해당 초만큼 기다리되 게시되면 즉시 응답 |
| 이미 게시됨 또는 미편성 | 기다리지 않고 즉시 응답 |

최대 대기 동안 게시가 없으면 HTTP 200과 `accepted:false`가 온다. 이는 통신 오류가 아니다. 다시 요청한다. HTTP 클라이언트 제한시간은 `wait`보다 길어야 하며, 기다림이 주행·인식 루프를 막지 않도록 배경에서 수행한다. 기다리던 팀들은 게시 시점에 응답받는다.

성공 응답은 `accepted:true`와 `order`를 포함한다. `order.tactical_command`는 명령문, `order.issued_at`은 **KST `YYYY-MM-DD HH:MM:SS`** 게시 시각이다. 실패 응답은 `accepted:false`와 `reason`을 포함한다.

| 정확한 reason | 뜻 |
| --- | --- |
| `임무는 경기 진행이 시작되면 게시됩니다` | 0:00 이전 |
| `이 경기에 편성되지 않은 팀입니다` | 기다려도 해당 팀 임무가 오지 않음 |
| `게시된 임무가 없습니다` | 게시되어야 할 시각이 지났는데 없음; 운영자 확인 필요 |

401은 임무코드 오류, 422는 `mission_code` 누락 등이다. 게시 전·미편성은 200 응답이다. 게시 후에는 경기 종료·프로그램 재시작 후에도 같은 명령을 돌려준다. M5의 실제 목표거점은 이 창구가 아닌 `/target`에서 받는다.

현재 구현은 `wait_s=20`을 기본값으로 사용하고 1~120으로 제한한다. 긴 연결의 중간 장비 유휴 제한을 줄이기 위한 클라이언트 선택이며, 120초를 지원하지 않는다는 뜻이 아니다. 제한시간은 `wait + max(5초, 일반 timeout)`이다. 즉시 조회가 필요한 진단에는 공식적으로 허용되는 `wait=0`을 사용할 수 있다. 서버가 120 초과 입력을 거부하는지 상한으로 줄이는지는 원문에 명시되지 않았으며 현장 확인 대상이다. 모의 서버는 요청 지시서에 따라 120으로 제한한다.

## 3. 출발·주행 — S3

출발과 주행을 보고하는 경기 HTTP 경로는 없다. UGV의 `/mil/match` 시작 신호와 젯슨 구동 API를 따른다. 시작 신호가 시계 0:00이며 `/me.phase == "running"`은 서버 측 진행 상태이다. 4:00 목표 게시, 5:00 또는 M5 점령 시 보고 단계로 연결된다. 임무 조회를 주행 승인이나 로봇 위치 복원의 대체 수단으로 사용하지 않는다.

## 4. 드론 영상 — S4

`GET /api/report/drone`은 최신 정상 JPEG 한 장을 받는 선택 기능이다. 기본 캡처는 1초 간격이다. 더 자주 요청해도 새 프레임이 더 빨리 생성되지 않는다. 깨진 영상은 전달하지 않고 다음 정상 영상까지 마지막 정상 영상을 유지한다. 따라서 수신 시각만으로 새 프레임으로 판단하지 않고 `X-Captured-At`을 확인한다.

| 요청 | 조건·동작 |
| --- | --- |
| `camera` 없음 | 경기 요청. 현재 경기 편성 팀이 `running`일 때 본선 카메라 수신 |
| `camera=main/test1/test2` | 테스트 모드가 켜진 연습 요청. 경기·편성과 무관하게 1초 간격, 시설 파괴에 따른 저하 없음 |
| 테스트 모드가 꺼진 상태에서 `camera` 지정 | `camera`는 무시되고 경기 규칙 적용 |

테스트 기간에도 `camera`를 생략하면 경기 요청이다. 경기에서는 `camera`를 붙이지 않는다. `main`은 본선, `test1`·`test2`는 테스트경기장 카메라이다.

**우리 진영 시설물**이 파괴되면 우리 영상이 저하된다. 이는 상대 팀의 지정표적이 파괴되는 경우이다.

| 우리 진영 파괴 수 | 새 장 간격 |
| --- | --- |
| 0 | 1.0초 |
| 1 | 2.0초 |
| 2 | 5.0초 |
| 3 | 영상 제공 불가, 403 |

| HTTP 200 헤더 | 규격 |
| --- | --- |
| `Content-Type` | `image/jpeg` |
| `X-Captured-At` | KST `+09:00`을 포함하는 캡처 시각 |
| `X-Frame-Interval-S` | `1.0`, `2.0`, `5.0` |
| `X-Camera` | `main`, `test1`, `test2` |
| `X-Test-Mode` | 연습 `on`, 경기 `off` |
| `X-Camp` | 경기 요청만, `BLUE` 또는 `RED` |
| `X-Destroyed` | 경기 요청만, `0`~`2` |

오류는 401, 403(3개 파괴), 409(편성·단계 조건 불충족), 422(코드 누락·잘못된 camera), 503(화면 없음·카메라 수신 꺼짐)이다. 원문이 완전히 제시한 단계 오류는 `드론 화면은 경기 진행 중에만 받을 수 있습니다 (지금: 보고)`이며, 테스트 모드가 아닌데 camera를 붙인 409에는 `— 지금은 테스트 모드가 아닙니다`가 덧붙는다. 미편성 문구는 원문에서도 `지금 경기에 편성된 팀만 …`으로 생략되어 있다.

현재 클라이언트는 캠프를 `/me`와 대조하고 `/me`를 권위 있는 정보로 유지한다. `/me` 실패 중에는 헤더 캠프만 임시로 참고하며 슬롯을 만들어 내지 않는다. 카메라·테스트 모드, 파괴 수·간격의 불일치는 경고한다. 유한한 양수 간격만 사용하고 잘못된 값에는 1초 기본값을 사용한다. 헤더 파괴 수는 방어적으로 0~2 범위로 제한한다. 이 보정은 서버가 잘못된 값을 준다고 보장하는 규칙이 아니다.

리허설 접두사에는 `/drone`이 없다. 영상은 `/api/report/drone?camera=...`에서 받는다.

## 5. M1 명령 해석 — S5

명령문은 주최측 **텍스트 LLM API**로 해석하여 지정표적·탐색 섹터·목표거점을 보고한다. 주최측 LLM 주소·키·요청 형식은 아직 안내되지 않았다. 배점은 지정표적 3, 탐색 섹터 3, 거점 4로 총 10점이다. 지정표적 정답은 해당 팀의 M2 표적과 같다. M1의 탐색 섹터·거점은 실제 M3 채점 구역·M5 2차 목표와 다를 수 있다.

`POST /api/report/interpretation`의 현재 **임시 JSON 형식**은 다음과 같다. `<임무코드>`는 형식 설명용이며 실행용 값이 아니다.

```json
{
  "mission_code": "<임무코드>",
  "target": "RED_RADAR",
  "search_sectors": ["R-S1", "CM"],
  "base": "RED_SUPPLY_DEPOT"
}
```

`target`·`base`는 시설물 보고값을 사용한다. ‘레이더시설’ 같은 한글 명칭은 422이다. `search_sectors`는 이름 목록이며 순서는 채점에 영향을 주지 않지만 섹터 누락·추가는 오답이다. 값은 대소문자를 구분하지 않는다. 시설 앞 진영은 **시설이 놓인 진영**이다. BLUE 팀의 상대 시설은 `RED_…`, RED 팀은 `BLUE_…`이다.

응답은 `accepted:true`, `received`이며 보고값은 대문자, 섹터는 이름 순으로 정리된다. 안 보낸 항목은 `null`이다. 다시 보내면 **전체 교체**한다. 거점만 새로 보내면 기존 표적·섹터는 지워진다. 가능한 세 항목을 매번 함께 보내고, 일부만 알 때 빠진 항목은 미보고 0점임을 인지한다. 보고할 항목이 하나도 없으면 422이다.

M1은 `running`에만 접수된다. 오류는 401, 409(단계·미편성·제외·UGV 미출발 0점 처리), 422(빈 보고·잘못된 시설값·숫자 섹터·중복 섹터·옛 `sector` 필드 등)이다. 정확한 단계 오류 예는 `명령 해석 보고(M1)는 '진행' 단계에서만 받습니다 (지금은 '준비')`이다.

현재 코드에서 미안내 LLM 요청 형식을 만들지 않는다. `Config.llm.endpoint`, `MAICON_LLM_API_URL`, 키가 들어갈 환경변수 이름 `MAICON_LLM_API_KEY`, 명시적 `--llm-factory module:function` 어댑터를 사용한다. 어댑터가 없으면 규칙 파서로 동작한다. 기본 `m1_llm_timeout=6초`이며 늦거나 실패한 결과를 기다리느라 최초 보고를 막지 않는다. 이는 개발·통신 실패 시 동작이고, 현장에서는 주최측이 배포한 LLM 사용 규격을 추가 확인해야 한다.

## 6. M2 지정표적 타격 — S6

각 팀이 지정받은 상대 진영 표적 한 개를 레이저로 타격한다. 참가팀이 HTTP로 타격을 보고하지 않는다. 젯슨 발사 명령, UGV 코드를 실은 레이저, 주최측 표적 수광 장치가 판정·전송을 담당한다. 표적 수광부를 **2초 연속** 비추면 유효타격이다.

누가 쐈는지와 관계없이, 상대 팀이나 아군 오사로 파괴되어도 그 표적을 지정받은 팀에 10점이 귀속된다. 연합 세 팀의 지정표적이 모두 성공하면 각 5점을 더 받는다. 표적은 경기마다 **최초 파괴 한 번만** 인정되므로 이미 부서진 표적을 재타격해도 추가 점수가 없다.

표적은 진영마다 통신시설·감시초소·레이더시설 세 개다. 가능한 위치는 공개되지만 위치별 종류는 경기마다 달라진다. 어느 것이 우리 표적인지는 별도 응답이 아닌 1차 명령문에서 읽는다. 파괴 여부는 참가팀 API로 제공하지 않는다. 관측 증거로 재타격을 피하고, 우리 진영 파괴에 따른 드론 저하를 고려한다.

## 7. M3 객체 인식 — S7

`POST /api/report/detection`으로 카메라로 확인한 구역별 종류·개수를 보고한다. **상대 진영 세 구역은 각 7점, CM은 9점**이다. 각 구역의 종류와 수량이 완전히 일치해야 해당 구역 점수를 받는다. M1에 나온 탐색 구역과 무관하게 채점 구역은 진영으로 고정된다.

| 우리 진영 | M3 채점 구역 |
| --- | --- |
| BLUE | `R-S1`, `R-S2`, `R-S3`, `CM` |
| RED | `B-S1`, `B-S2`, `B-S3`, `CM` |

현재 **임시 JSON 형식**은 다음과 같다.

```json
{
  "mission_code": "<임무코드>",
  "sectors": [
    {"sector": "R-S1", "objects": [{"type": "tank", "count": 2}]},
    {"sector": "R-S2", "objects": []},
    {"sector": "R-S3", "objects": []},
    {"sector": "CM", "objects": [{"type": "drum", "count": 1}]}
  ]
}
```

`sectors`는 1~7개 목록이고 같은 섹터를 두 번 쓰지 않는다. 객체가 없으면 해당 섹터의 `objects`를 `[]`로 쓴다. 한 구역의 같은 종류는 합쳐 한 항목으로 보고하며 count는 정수 0~99이다. 보고값 type은 아래 여섯 종류뿐이다.

| 그림 | 보고 type | 내부 이름 |
| --- | --- | --- |
| 군용트럭 | `military_truck` | `TRUCK` |
| 박격포 | `mortar` | `MORTAR` |
| 전차 | `tank` | `TANK` |
| 미사일 | `missile` | `MISSILE` |
| 탄약상자 | `ammo_box` | `AMMO_BOX` |
| 드럼통 | `drum` | `DRUM` |

전차는 판에 붙은 그림이며 상대 UGV가 아니다. 파괴건물·방호벽·야전진지·차단벽 등의 다른 그림, 장애물, 블록 겉면을 보고하면 틀린다. 위에서 찾은 0.4m 큐브는 지상에서 확인할 **탐색 후보**이며 사진 종류의 정답은 아니다.

응답은 `accepted:true`, `received.sectors`이다. 섹터를 정리하고 type을 대문자로 반환한다. 섹터·객체의 정확한 출력 순서는 정답 여부를 결정하는 내용이 아니다. 다시 보고하면 **빠진 구역의 과거 값도 사라지는 전체 교체**이다. 다른 진영 구역도 접수하지만 채점하지 않는다.

`running`에만 접수되며 서버 수신 전에 단계가 바뀌면 409이다. 오류는 401, 409(단계·미편성·제외·UGV 미출발), 422(섹터·종류 중복, 숫자 섹터, 알 수 없는 종류, count 범위·형식 등)이다. 정확한 단계 오류 예는 `객체 인식 보고(M3)는 '진행' 단계에서만 받습니다 (지금은 '보고')`이다.

현재 구현은 완전한 최신 보고를 변경 시 다시 보내며, 기본 재보고 간격은 5초, 225초부터 `m3_late_gap_s=1초`이다. STOP 또는 보고 단계 이후 새 M1·M3를 만들지 않고 남은 큐도 닫는다. 서버 수신 마감에 앞선 여유를 둔다. 시뮬레이터의 `points`·`official_exact`는 공식 구역 점수이고, `recall`·`precision`·기존 `exact`는 개수 비교 진단이다. 미보고 구역과 빈 객체 목록을 명시한 구역은 구분한다.

## 8. M4 상대 UGV 타격 — S8

참가팀 HTTP 보고는 없다. 발사는 젯슨 API를 사용하고, 피격 UGV의 주최측 ESP가 판정한다. 목숨은 4로 시작하며 경기 끝 남은 목숨으로 유효피격 횟수를 계산하고 심판 정정도 반영한다.

| 유효피격 | 0회 | 1회 | 2회 | 3회 | 4회 이상 |
| --- | --- | --- | --- | --- | --- |
| M4 점수 | 15 | 12 | 8 | 3 | 0 |

수광부에 2초 연속 조사해야 유효피격이다. 피격 후 10초 동안은 무적이므로 추가 피격으로 세지 않는다. 아군이 쏴도 피격으로 센다. 아군 사선·오사를 피하고 생존을 우선하는 기존 회피 정책을 유지한다. 경기 중 점수·목숨을 참가팀 HTTP API로 받는 기능은 없다.

## 9. M5 목표거점 — S9

4:00에 **진영별 한 곳**을 `GET /api/report/target`으로 받는다. 경기 시작부터 긴 폴링을 걸어 두고 `/order`와 같은 wait·제한시간·배경 처리 규칙을 적용한다. 명령문은 포함하지 않는다.

성공은 `accepted:true`와 `order`이며, `order.objective`는 시설 보고값, `order.objective_label`은 작전지휘소·정비소·군수보급소 중 하나, `order.issued_at`은 KST `YYYY-MM-DD HH:MM:SS`이다. BLUE 팀의 목표는 `RED_…`, RED 팀의 목표는 `BLUE_…`이다.

| 정확한 reason | 의미 |
| --- | --- |
| `M5 목표거점은 종료 60초 전에 게시됩니다` | 게시 전 |
| `이 경기에 편성되지 않은 팀입니다` | 미편성 |
| `게시된 임무가 없습니다` | 게시 시각 이후 내용 없음; 운영자 확인 |

게시 전·미편성은 200과 `accepted:false`이고, 코드 오류는 401, 코드 누락 등은 422이다. 게시 뒤에는 경기 종료 후에도 같은 목표를 받는다. **M1에 나온 거점과 달라도 M5는 `/target` 결과를 따른다.** 점령 결과를 별도 참가팀 API로 받지는 않는다.

점령은 게시 이후 목표거점 센서가 처음 가려지는 순간 판정된다. 센서는 어느 UGV인지 모르므로 **우리 UGV가 우리 거점에 들어가도 그 거점이 상대의 목표이면 상대 점령**이다. 목표가 아닌 거점에 들어가면 점수·종료가 발생하지 않는다. 두 연합이 거의 동시에 진입하면 센서 감지 시각이 이른 쪽, 그 차이가 센서 시각 오차 약 10ms 이내이면 서버에 먼저 도착한 쪽이 우선한다.

점령하는 순간 진행이 끝나고 점령한 연합 세 팀이 각각 10점을 받는다. 점령한 개별 팀의 별도 몫은 없다. 경기 종료 후 연합 합계가 높은 쪽의 세 팀에 각각 5점을 더 주며, 무승부이면 양쪽 모두 5점이다.

센서 앞 체류 시간은 **잠정**이다. 현재는 가려지는 순간이며 `mission.m5_dwell_s=0.0`을 설정 슬롯으로 유지한다. 실제 센서 위치·체류시간은 확인해야 한다. Python 시뮬은 기존 거점 내부 영역을 센서 대역으로 사용하고 같은 계산 틱 사건은 모의 수신 순서로 다룬다. 실물의 10ms 측정 오차를 검증했다는 뜻이 아니다. 운영 전략의 우리 거점 접근 금지는 기본 225초부터 적용하여 4:00 이전에 대비한다.

## 10. 경기 종료·보고 전환 — S10

5분이 되거나 M5 점령이 일어나면 주최측이 UGV를 멈추고 잠근다. **서버는 먼저 `/me.phase`를 `reporting`으로 바꾸고 그다음 로봇에 `report`를 보낸다.** 따라서 phase 변화만 먼저 관측해도 M6를 시작한다. 팀 프로그램은 보고를 위해 계속 실행한다.

`pause`는 경기 도중 일시정지이며 종료가 아니다. 재개나 report가 이어질 수 있고, pause만으로 M6를 보내지 않는다. `reporting`이 아니면 M6는 409이다.

보고 시간은 **서버가 reporting으로 바꾼 순간부터 30초**이며 남은 시간을 제공하지 않는다. 여섯 팀이 모두 M6를 내면 30초 전에도 즉시 종료한다. `finished`에서 주최측이 프로그램을 종료하므로 뒤늦은 전송은 불가능하다. 이 구간에 받는 보고는 M6뿐이며 M1·M3는 409이다. M2·M4·M5는 계속 장치 판정 영역이고 참가팀 보고 창구를 만들지 않는다.

## 11. M6 위험도 보고 — S11

경기 중 상대 세 팀의 순위를 미리 추정하고, 보고 단계로 바뀌면 지체 없이 `POST /api/report/situation`으로 보낸다. 409면 단계를 확인하며 잠시 뒤 재시도한다. 보고 기간 안에서 고쳐 보내면 마지막 것이 남는다. 한 팀의 첫 보고가 다른 다섯 팀의 보고와 합쳐져 즉시 종료될 수도 있으므로 후속 정정을 보장할 수 없다.

현재 **임시 JSON 형식**은 `{"mission_code":"<임무코드>","ranking":["R-2","R-1","R-3"]}`이다. ranking은 위험한 순서로 상대 진영 호출부호 1~3개를 적는다. BLUE 팀은 `R-1`~`R-3`, RED 팀은 `B-1`~`B-3`이다. 대소문자는 정규화하여 응답 `received.ranking`에는 대문자가 온다. 순위 배열의 순서는 의미가 있다. `R-2`는 팀 호출부호이고 `R-S2`는 섹터이므로 혼용하지 않는다.

공식 위험도는 다음과 같다.

```text
위험도 = max(0, 남은 목숨)/4 + max(0, 남은 탄)/8 + max(0, M3 점수)/30
```

세 항은 같은 무게다. 셋 다 맞으면 15점, 1순위를 맞히면 10점, 2·3순위 중 하나를 맞히면 5점이다. **동점일 때 서로 바꿔도 맞다는 처리는 잠정**이다. 현재 평가 코드는 안정적인 ID 순서로 동점을 표시하며 잠정 동점 인정 규칙을 확정적으로 확대하지 않는다.

서버는 상대나 자기 점수를 제공하지 않는다. 로봇의 M6 추정은 관측한 피격·LED·탄약 증거, 이동·방문 흔적 등으로 수행한다. 평가용 시뮬 정답은 실제 남은 상태와 접수된 M3 구역 점수로 계산하며, 이 숨은 상태를 로봇의 추정 입력으로 넘기지 않는다.

오류는 401, 409(보고 단계 아님·미편성·제외), 422(자기 진영·중복 호출부호·형식 오류·ranking 누락 등)이다. 정확한 단계 오류 예는 `상황보고는 '보고' 단계에서만 받습니다 (지금은 '진행')`이다. 마감까지 M1·M3·M6를 보고하지 않았으면 해당 임무는 0점이다. 이후 운영진 점수 확인, 프로그램 종료, UGV 회수 순서이다.

## 부록 A. 보고값·구역·오류 — SA

| 시설 | BLUE 진영 보고값 | RED 진영 보고값 | 용도 |
| --- | --- | --- | --- |
| 작전지휘소 | `BLUE_COMMAND_POST` | `RED_COMMAND_POST` | M1 base, M5 objective |
| 정비소 | `BLUE_MAINTENANCE` | `RED_MAINTENANCE` | M1 base, M5 objective |
| 군수보급소 | `BLUE_SUPPLY_DEPOT` | `RED_SUPPLY_DEPOT` | M1 base, M5 objective |
| 통신시설 | `BLUE_COMMS` | `RED_COMMS` | M1 target, M2 |
| 감시초소 | `BLUE_OUTPOST` | `RED_OUTPOST` | M1 target, M2 |
| 레이더시설 | `BLUE_RADAR` | `RED_RADAR` | M1 target, M2 |

섹터는 `B-S1 B-S2 B-S3 CM R-S1 R-S2 R-S3` 일곱 이름이다. 숫자 1~7은 422이며 대소문자는 구분하지 않는다. 각 진영 위에서부터 1·2·3행이고 거점·호출부호와 행 번호가 같다. 좌우 끝 거점 띠는 어느 섹터도 아니다. 내부 `COMMON`은 송신 시 `CM`으로 변환한다.

| HTTP 코드 | 공식 의미 |
| --- | --- |
| 401 | 임무코드 오류. 정확한 문구는 항상 `임무코드가 올바르지 않습니다` |
| 409 | 현재 단계·편성에서 접수하지 않음. 단계 오류에는 현재 단계 이름이 포함됨 |
| 422 | 형식 오류. `detail` 목록의 각 항목에 `loc`와 `msg` |
| 403·503 | 드론 영상에만 해당 |

성공 응답 형식은 창구마다 다르다. 오류는 `detail`을 가진 JSON 본문으로 안내되어 있다. **원문이 명시한 422 형식은 `loc`·`msg` 목록**이다. 문자열·dict·비JSON 오류도 클라이언트가 안전하게 요약하고 가리는 것은 방어적 처리이며, 공식 서버가 그 모든 형태를 보장한다는 뜻이 아니다. 모의 서버의 주입 기능으로 이러한 통신 결함을 시험한다.

원문이 생략한 `이번 경기에서 빠진 팀입니다 — …`, `이번 경기에서 UGV가 출발하지 못해 0점 처리된 팀입니다 — …`, 드론 미편성 문구의 뒷부분 등은 창작하지 않는다. 코드의 `schema.ERROR_DETAILS_UNSPECIFIED`가 전체 문구 확인이 필요한 사유를 표시한다. 완전한 원문 문자열과 생략된 접두를 구분한다.

## 부록 R. 리허설 — SR

운영자가 리허설을 열어 둔 기간에 참가팀 포털의 테스트 대시보드에서 ‘리허설 준비’와 ‘시작’을 사용한다. 실제 경기 기록·점수에는 남지 않는 한 판이며 요청·응답 형태는 경기와 같다. 우리 UGV 연결과 연습 호출부호 배정이 필요하고 막힌 이유는 포털에서 확인한다.

허용되는 일곱 경로는 `/api/rehearsal/me`, `/ready`, `/order`, `/target`, `/interpretation`, `/detection`, `/situation`이다. GET·POST 메서드와 임무코드 위치는 경기와 같다. `/api/rehearsal/drone`은 없고 연습 영상은 경기 접두사의 `/drone?camera=...`를 사용한다.

준비 단계에서 UGV가 잠기고 프로그램이 실행되어 준비완료를 보낸다. 운영자가 **시작을 누른 5초 뒤가 0:00**이다. 4:00 목표 게시, 5:00 진행 종료, 보고 30초 후 5:30 종료를 따른다. 끝나면 포털에서 받은 보고와 M1 정답 비교를 볼 수 있다.

리허설이 없으면 `/me.phase`는 `idle`, `/order`·`/target`은 `accepted:false`와 `진행 중인 리허설이 없습니다`이다. 리허설에서도 M1·M3는 진행 중, M6는 보고 단계만 받으며 같은 409·422 규칙을 적용한다.

## 현재 구현의 통신·재시작 정책

보고 형식과 검증은 `maicon26/link/schema.py`, 내부·보고값 대응은 `maicon26/vocab.py`가 담당한다. 임시 JSON을 여러 모듈에 별도로 정의하지 않는다. `equal_received`는 M1 섹터와 M3 섹터·종류의 순서·대소문자를 정규화하여 비교하고, 누락·추가·수량 차이는 구분한다. M6는 순위를 유지한다. 같은 내용의 응답 불일치에는 경고 한 번과 최대 한 번 재전송 예산을 적용한다.

조회 reason은 의미별로 분류한다. 게시 전은 최소 0.5초 간격, 미편성은 `/me`와 교차 확인하며 10초 간격, 게시 누락은 경고 후 5초 간격, 리허설 없음은 대기 안내 후 5초 간격으로 다시 조회한다. 동일한 상태에 대해 매 요청마다 로그를 늘리지 않는다. 미편성·제외·UGV 미출발 제출 409는 해당 경기의 그 보고 종류 재시도를 닫고, 새 경기의 `idle`·`waiting` 상태에서 초기화한다. `/ready` 409는 사유가 영구적으로 보여도 공식 절차대로 2초 간격으로 다시 확인한다.

`scripts/run_real.py`는 모델 추론과 필수 센서·TF·항법 초기화 후 서버 상태를 확인한다. HTTP는 항상 `AsyncServerLink`로 감싸 제어 루프와 분리한다. `--rehearsal`은 리허설 접두사를 선택하고 `--drone-camera main|test1|test2`는 리허설 진단에서만 허용한다. 일반 연습 영상 API 자체의 공식 조건은 앞의 S4와 같으며, 이 CLI 제한은 실수 방지를 위한 실행 정책이다.

임무코드 입력은 `MAICON_CODE`, 호환 환경변수 `MAICON_MISSION_CODE`, `--code-file`, 숨김 입력(getpass) 순서이다. 숨김 입력은 최대 세 번 형식을 확인한다. 환경변수·파일의 형식 불일치는 값을 노출하지 않는 경고 후 현장 서버 확인을 계속한다. 입력의 대소문자는 서버 전송 전에 바꾸지 않는다. 임무코드를 명령행 값으로 받지 않으며, 제거된 `--mission-code` 옵션을 써도 그 값을 오류로 되찍지 않는다.

HTTP `Date`와 로컬 단조 시계를 연결한 뒤 `order.issued_at`으로 경기 경과 시간을 복원할 수 있다. `Date`는 일반 HTTP 헤더이지 추가 경기 API 필드가 아니다. 동기화 전, 잘못된 게시 시각, 음수 또는 300초 초과 경과값은 받아들이지 않는다. 정수 초 표현과 왕복 지연 때문에 정확도가 제한되며 구현은 `1초 + RTT/2`의 시각 불확실성을 기록한다. `target.issued_at`은 4:00 간격 교차 검증용이며 틀렸다고 목표거점이나 시작 시각을 임의로 바꾸지 않는다.

**시계 복원은 SLAM 지도·현재 위치·좌표 앵커 복원이 아니다.** HTTP/Agent의 시간 복원 기능이 있어도 실기 실행기는 경기 중 새 프로세스가 출발 거점에 있다고 가정하여 주행을 재개하지 않는다. 로컬 초기화 후 `/me`를 읽고, 이미 `reporting`이면 첫 제어 틱 전에 STOP을 래치하여 M6 보고를 수행할 수 있다. `finished`이면 정지한 채 종료한다. 안전한 진행 중 주행 재개에는 별도의 위치·지도 복원이 필요하다.

`maicon26/sim/mockserver.py`는 소켓을 열지 않는 모의 서버이다. 실제 HTTP 요청 대신 동일한 transport 계약을 사용하며 가상 시계로 수신 마감·게시·긴 폴링을 재현한다. 준비 오류, 정규형 검증, 출력 순서 변경, 드론 마지막 정상 프레임·헤더·저하, 리허설, 여섯 팀 M6 조기 종료, 지연·응답 손실·중복·비JSON·오류 상태를 시험한다. 이 시험 결과는 실서버 접속 성공이나 실물 카메라·센서 성능의 증거가 아니다.

## 잠정 항목과 현장 확인

| 항목 | 현재 취급 |
| --- | --- |
| M1·M3·M6 JSON | 안내서의 임시 형식을 schema 한 곳에서 구현; 최신 배포 형식 재확인 |
| 주최측 LLM | 주소·키·요청 형식 미안내; 설정 슬롯과 명시적 어댑터만 제공 |
| M6 동점 | 서로 바꿔도 맞음은 잠정; 특별한 확정 규칙으로 확대하지 않음 |
| M5 센서 체류 | 기본 0초, 실물 규격 확인 후 설정 |
| 실제 서버 주소·임무코드 | 현장 별도 안내, 저장소·로그·문서에 실제 값 미포함 |
| 생략된 오류 문구 | 알려진 접두만 사용; 완전한 서버 응답 확인 필요 |
| wait 120 초과 입력 | 최대 120 지원은 확정, 초과 입력의 서버 처리 방식은 미명시 |
| 실물 시각·센서 경계 | 장치 시각 오차, 센서 설치 위치, 지연과 주행 재개 조건 현장 확인 |

추출 본문을 기준으로 누락을 점검하되 SVG 근거도 함께 대조한다. 요청 지시서의 추정 저장소 지도·테스트 수·기존 버그 설명은 사실 확인 대상이며, 안내서 원문과 충돌하면 원문을 우선한다. 현재 변경사항과 검증 결과는 작업 기록 및 추적표에 따로 남긴다.
