# Gazebo 실제 렌더링 영상 녹화

## 2026-11-09 검증 결과

고정 경기장·랜덤 배치 시드 2에서 B2 단독 UAV 미수신 실험
[`b2_no_uav_third_20261109_v7.mp4`](../ros2/gazebo/recordings/b2_no_uav_third_20261109_v7.mp4)는
M3 채점 대상 **12/12**, 추가 계수 **0**, M5 **248.5초 진입**, 최종 위치 오차
**0.008m**로 개발 합격 기준을 통과했다. 모의 판정 충돌 카운터는 0이었다.
실제 서버 제출 스냅샷은 4구역을 포함하며 마지막 수신은 222.769초,
총 15회였다. 영상은 960×720·5fps·252초이며 전체 1,260프레임 디코딩과
6개 시점의 시각 검사를 통과했다. 위치 오차는 평가에만 사용하는 Gazebo
실제 위치와 비교한 값이다. 분류는 모의 검출이므로 실제 영상 모델의 100%
탐지율이나 다른 배치에서의 성공을 보장하는 결과는 아니다.

## 실행

경기 시뮬레이션과 녹화를 함께 실행한다. 기존 파일은 덮어쓰지 않는다.

```bash
# B2 단독, UAV 영상·위치 정보 모두 처음부터 받지 않는 조건, 3인칭
VIEW=thirdperson PHYSICAL_ROBOTS=one UAV_LAYOUT=off UAV_SCHEDULE=0:off \
  SLAM=arena LIDAR_MODE=sectors360 SIM_EFFECTIVE_TRACK=.20473 REQUIRE_PERFECT_M3=1 \
  OUTPUT="$PWD/ros2/gazebo/recordings/b2_no_uav_thirdperson.mp4" \
  bash scripts/run_gazebo_fpv_trial.sh

# 3대3, 보정된 실제 UAV 영상 + 중간 수신 단절, 3인칭
VIEW=thirdperson PHYSICAL_ROBOTS=six SLAM=arena LIDAR_MODE=sectors360 SIM_EFFECTIVE_TRACK=.20473 \
  UAV_CALIBRATION=ros2/gazebo/uav_four_corner_calibration.json \
  UAV_SCHEDULE=60:off,160:1 REQUIRE_PERFECT_M3=1 \
  bash scripts/run_gazebo_fpv_trial.sh
```

`LIDAR_MODE=sectors360`은 같은 센서 위치의 120도 측정 3개를 동기화해
360도 스캔으로 합친다. 없는 방향의 거리를 만들어 넣지 않는다. 자기 차체
안쪽의 반사는 알 수 없는 방향(NaN)으로 처리한다. 기본 `sector160` 모드는
비교용으로 남겼다. 현재 WSL의 GPU에서는 최소 거리만 출력되는 문제가
재현돼 센서 렌더링은 `SIM_LIBGL_ALWAYS_SOFTWARE=1`을 사용한다.
CPU 방식의 별도 정지 시험에서 360점·9.9Hz 측정을 확인했다. GUI는
별도로 `GUI_LIBGL_ALWAYS_SOFTWARE=0`을 선택할 수 있다.

`SLAM=arena`는 이 고정 경기장의 기존 벽·13개 구조물 도면과 알려진 B2 출발
거점을 사용하는 선택 모드다. 랜덤 M3 박스 위치와 Gazebo 실제 로봇 위치는
위치추정 입력이 아니다. 실제 LiDAR·바퀴 관측을 대조하며 위치추정 근거가
부족하거나 센서가 오래되면 정지한다. 일시적 전달 지연은 정지 상태에서 최대
2초 기다리고, 회복되지 않으면 실패 보고서를 남긴다.

`.20473` m는 이 Gazebo Rover의 좌·우 회전 실측으로 얻은 유효 바퀴 간격이다.
실제 CAD 바퀴 위치는 0.17452 m로 유지한다. 보정 전 회전량 오차 약 17.3%가
별도 양방향 회전 재시험에서 0.1% 미만으로 줄었다. 이 값은 실제 로봇의
보정값이 아니며, 접촉·마찰 설정을 바꾸면 다시 측정해야 한다.

`REQUIRE_PERFECT_M3=1`은 진영별 네 채점 구역에서 제출 수량의 누락·추가 계수가 모두 없고 M5 진입도
성공해야 실행 성공으로 처리한다. 실패 영상과 결과도 그대로 보존한다.
이는 개발용 엄격한 합격 기준이며 PDF에 명시된 일괄 0점 규칙을 뜻하지 않는다.
기본 실험은 300초, 거점 명령 240초, M3 박스 4개(16면)이다. 이 박스 수는
실험 설정이며 대회의 확정 배치·수량을 뜻하지 않는다.

M3는 BLUE에게 R-S1·R-S2·R-S3·CM, RED에게 B-S1·B-S2·B-S3·CM이 채점 구역이다.
기본 시드 2의 물리 사진 16면 중 BLUE의 채점 대상은 12면이다. M1 명령의
시설 탐색 구역으로 M3를 제한하지 않는다. 제출은 10초부터 시작해 변경된
전체 결과를 5초 간격으로 보내며, 280초에 최종 전체 제출, 290초에 모든 M3
재시도까지 닫는다. 매번 네 구역·6종의 현재 결과를 모두 구성하므로 한 구역의
새 발견 때문에 다른 구역의 이전 결과가 빠지지 않는다. 서버는 수신 시각이
300초 이상이거나 조기 종료된 뒤의 M3를 거부한다.

M3 제출에는 지정 6종의 확정된 사진 관측만 포함한다. 기본 최소 4표, 평균
신뢰도 0.65, 분류 우위 기준을 만족해야 하며 2표짜리 미확정 관측은 보내지
않는다. LiDAR로 면이 확인된 뒤에는 초기의 부정확한 위치·법선 기록을 별도
객체로 중복 집계하지 않는다. 명시적인 면 연결이 충분하면 같은 면의 분류에
근사 연결 표를 섞지 않는다. 이전 결과를 최대값으로 고정하지 않아 이후
증거에 따라 수량을 줄이거나 분류를 정정할 수 있다. 이 기준은 오인식 위험을
줄이며 실제 영상 검출기의 정확도를 보장하지 않는다.

현재 UAV 영상 모드는 영상에서 구조물 위치를 추출한다. 별도의 UAV 로봇
검출기는 아직 연결하지 않았으며 Gazebo 정답 위치로 그 결과를 보충하지 않는다.
3대3의 B2는 현재 임무 코드, 나머지 5대는 순찰·교전 스크립트로 움직인다.

`VIEW=thirdperson`은 경기장 남쪽 위에 고정한 사선 카메라로 경기장 전체와
로봇의 이동을 기록한다. 실제 Gazebo 센서가 만든 960×720, 5 Hz 영상이다.
카메라의 `/recording/arena/image`는 녹화기만 받으며 Agent의 인식·위치추정·
경로계획에는 전달하지 않는다. UAV 입력인 `/uav/image`와는 다른 영상이다.
이 모드에서는 B2 전방 녹화 센서를 추가로 실행하지 않는다.

기본값 `VIEW=firstperson`은 B2의 고정 전방 카메라를 640×360, 10 Hz로 기록한다.
팬·틸트 조준 방향을 따라 움직이는 카메라는 아니다. 두 시점 모두 시뮬레이션의
실제 영상이며 M3 객체 분류의 정확도를 검증하는 영상 인식 파이프라인은 아니다.

결과는 MP4, 경기 결과 JSON, 경로 PNG, 첫·마지막 프레임 PNG로 저장된다.
`.recording.json`에는 원본 프레임 수, 실제 수신 빈도, 영상 길이와 보간 없이
유지한 프레임 수를 기록한다. `.frames.jsonl`에는 각 저장 프레임의 원본 촬영
시각을 남긴다. 영상은 시뮬레이션 시간을 기준으로 재생하며, 짧은 수신 공백은
마지막 실제 프레임을 유지하고 1초를 넘긴 공백은 `CAMERA FRAME MISSING`으로
표시한다. 새 장면을 합성해서 채우지 않는다.

카메라만 별도로 녹화하려면 ROS 환경을 준비하고 다음을 실행한다. SIGINT 또는
SIGTERM으로 종료하면 MP4와 메타데이터를 마무리한다.

```bash
python3 scripts/record_gazebo_fpv.py --topic /recording/arena/image --fps 5 \
  --output ros2/gazebo/recordings/overview.mp4
```
