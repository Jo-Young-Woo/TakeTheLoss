# 상대 IMU 회전과 바퀴 오도메트리의 결합

실기 기본값과 v2는 `hal.imu_heading_fusion=false`를 유지한다. 검증용 Gazebo 실행에서만 켠다. 깊이 카메라와 Gazebo의 전역 자세는 입력으로 쓰지 않는다.

`maicon26/hal/imu_odometry.py`는 첫 바퀴 오도메트리 위치·방향에 정렬한 뒤, 유효한 IMU의 **회전 변화량**만 사용한다. IMU가 보고한 절대 방향을 지도 방향으로 넣지 않는다. 바퀴의 병진 변화는 원래 바퀴 방향의 중간 각도에서 차체 좌표로 돌린 다음, 결합한 중간 방향으로 다시 회전한다. 따라서 바퀴가 실제보다 많이 회전했다고 보고해도 그 잘못된 방향으로 병진이 누적되는 것을 줄인다. 바퀴 자체의 직진 미끄러짐까지 해결하지는 않는다.

ROS 전송 계층은 단위 쿼터니언, 유한한 공분산, 방향 사용 불가 표시, IMU 프레임을 검사한다. 차체에 고정된 IMU 장착 변환은 최신 TF로 한 번 검증하고 프레임 쌍별로 보관한다. 센서 시각으로 고정 장착 TF를 조회하면 전송 지연 때문에 ExtrapolationException이 났으므로 이 검사를 측정 시각과 분리했다. 반면 **IMU 측정값과 바퀴 측정값의 짝짓기는 원래 타임스탬프로 최대 0.15초**까지만 허용한다. 기울어진 장착은 이 구현에서 허용하지 않는다.

누락·역순·잘못된 IMU 값은 바퀴 변화량으로 돌아간다. 다시 유효해진 첫 IMU는 새 기준만 설정하고 바퀴 변화량을 유지하므로, 복귀 순간 절대 방향이 갑자기 바뀌지 않는다. 이후부터 새 IMU 변화량을 사용한다.

전송 객체의 `imu_odometry.diagnostics()`는 모드, 결합/대체 횟수, 원래/결합 위치, 측정 나이를 반환한다. `dump(path)`는 최근 최대 16,000개의 IMU·원래 바퀴·결합 샘플을 JSONL로 저장한다. 이 기록에는 평가 정답이 없다.

## 실제 센서의 짧은 읽기 전용 점검

기존 candidate01의 B3에서 20.02초의 벽시계 시간 동안 5.148초의 시뮬레이션 측정을 받았다. 기록은 `recordings/wingbot_selfplay_20261109_candidate01/B3_heading_audit_clock.json`이다.

| 측정 | 첫 시점의 평가 방향과 차이 | 구간 내 상대 회전 오차 p95 | 최대 |
|---|---:|---:|---:|
| 바퀴 오도메트리 | 64.270° | 1.871° | 2.271° |
| IMU | −0.029° | 0.374° | 0.433° |

Gazebo 자세는 이 독립 점검의 평가에만 사용했다. 해당 TF 헤더 시각이 0이므로 가장 최근 수신한 시뮬레이션 시계를 붙인 **수신 시각 근사**다. 따라서 시간 정합 오차가 있고, 이 표는 전체 임무에서 위치 정확도가 개선됐다는 증거가 아니다. 누적 바퀴 방향 오차와 상대 IMU 회전을 비교할 이유를 보여준다.

단위 검증은 바퀴만 회전하는 경우, IMU 90°/바퀴 180°, ±π 경계, 누락 후 복귀 연속성, 병진 좌표 방향, 공분산·프레임·역순 시각 거부, 최신 고정 장착 TF 확인을 포함한다. 최초 실제 혼합 smoke02에서는 고정 장착 TF의 정확 시각 조회가 실패하여 모든 샘플이 바퀴 대체로 처리됐다.

최신 TF 검증으로 수정한 실제 `wingbot_mixed_allies_smoke_20261109_03`의 여섯 프로세스는 모두 정상 종료했다. 각 로봇의 최종 모드는 `imu_relative`, 결합 횟수는 218~221회, 시작 구간 바퀴 대체는 1~2회, 거부한 IMU는 0~1회였다. 예를 들어 B-3는 220회 결합했고 원래 바퀴·IMU·결합 기록 453개를 저장했다. 기록은 각 로봇 폴더의 `imu_odometry.jsonl`과 `imu_odometry_summary.json`이다. 이는 실제 ROS/TF 경로가 동작한다는 확인이며, 전체 임무·실기 수용 여부는 별도 A/B 결과로 판단한다.
